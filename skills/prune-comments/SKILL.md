# Prune comments

Comments in this codebase are LLM-generated by default. They restate the code, narrate the session that produced them, or justify a decision nobody will re-litigate. Delete them freely — no guilt, no archaeology. The code is the record.

A comment survives only if a competent reader of the code still cannot answer *what this value is* or *why this shape is required*.

**Authorship is not a signal.** Do not judge how a comment was written — assured, well-phrased rationale prose is the house style of a generator, not evidence of a human hand. There is no "these ones look deliberate, so this repo is different" exemption; there is no whole-repo verdict at all. Classify one comment at a time against the test above. If a prose paragraph passes, the fact inside it passes — cut it to the fact and drop the prose.

## Code carries its own meaning

Before keeping any comment, ask whether the code could say it instead. A comment that compensates for unclear code is a bug report about the code. Fix the code:

| Comment doing the work | Code that replaces it |
|---|---|
| `// 900 = 15 min in seconds` | `const SESSION_TTL_SECONDS = 15 * 60` |
| `// check the user can still edit` | `if (canStillEdit(user, doc))` |
| `// this block normalises the payload` | extract `normalisePayload(raw)` |
| `// x is the retry count` | rename `x` to `retryCount` |
| `// returns null when not found` | make the return type `User \| null` |

Only what naming genuinely cannot carry stays as a comment: a derivation, a spec citation, an external bug, a constraint that lives outside this file.

These edits are allowed even though the diff is otherwise comment-only — but they must be **behavior-preserving and mechanical**: name a value, extract a block, rename a local. No restructuring, no signature changes to anything outside the file, no logic changes. Report them separately from the deletions.

If the fix is not mechanical (needs a wider refactor, touches a public API, changes control flow), do not do it. Keep the comment and say so in the report.

## Keep

Nothing reaches this list until it has failed the promotion test above. A comment explaining a *value* is a named constant that hasn't been written yet — the comment stays only for the part a name cannot hold (the derivation, the citation, the consequence).

- **Magic numbers / opaque constants** — where the value comes from, once naming it is not enough: `// 2^53 - 1, max exact integer in IEEE 754`, `// SMTP hard limit, RFC 5321`. A bare unit or meaning becomes a named constant instead.
- **Mathematical or algorithmic logic** — the derivation, invariant, or complexity trick that the expression hides.
- **Fixes and workarounds** — a bug the code steps around, ideally with an issue/CVE/PR link: `// Safari < 16.4 fires resize before layout; measure on next frame`.
- **Non-obvious constraints** — ordering requirements, thread/lock rules, security reasons, "must stay in sync with X".
- **Load-bearing comments** — directives the toolchain reads (`@ts-expect-error`, `# noqa`, `//go:build`, `eslint-disable`, JSDoc types, docstrings, license headers). These are code wearing a comment costume. See [load-bearing-comments.md](load-bearing-comments.md) — read it before the first delete.

Rewrite a keeper that buries its point in narration. Keep the fact, drop the story.

## Delete

- Restatement: `// loop over users`, `// set the flag to true`, `// constructor`.
- Session history: "we refactored this to…", "previously this used X", "changed in the auth cleanup".
- Cherry-picked motivation: the single example that prompted the change — "this broke when Marie's tenant had 3 workspaces".
- Decision justification with no operational consequence: "chose a Map here for readability".
- Banners and dividers: `// ===== HELPERS =====`, `// --- end ---`.
- Redundant doc blocks: a `@param userId The user id` wall that adds nothing to the signature.
- Commented-out code. Git has it.
- Type restatements in a typed language.
- `TODO`/`FIXME` are work markers, not narration — leave them. Report stale-looking ones instead of deleting.

## How

1. **Scope it.** Only files the user named or the current diff. Never vendored, generated, or third-party trees (`node_modules`, `dist`, `*.generated.*`, `vendor/`).
2. **Read the file first.** Classification needs the surrounding code — a number is only magic if the reader can't source it.
   If the pass is large enough to need a written plan, that plan's keep list is already split in two: **kept as comment** and **promoted to code**. A plan whose promotion column is empty has skipped the test — go back and run it.
3. **Delete, or promote into code.** Remove the comment's own line and any blank line it orphaned. Where the comment existed because the code was unclear, apply the mechanical fix from *Code carries its own meaning* instead of keeping it. Nothing else — no reformatting, no "while I'm here" fixes.
4. **Verify** — mandatory, not optional:
   - `git diff -U0 -- <paths>` and read every changed hunk. Every non-comment line in the diff must be a promotion you can name; anything else is a bug — revert it.
   - Run the project's typecheck/lint/build/tests. Stripped directives and broken promotions both surface here.
5. **Report** — three lists: count removed per file, every promotion (comment → code change), every comment kept with a one-line reason. User can overrule any of them.

## Red flags

| Thought | Reality |
|---|---|
| "These comments read as hand-written, this repo is different" | Prose quality says nothing about authorship, and there is no repo-level verdict. Judge one comment at a time. |
| "The keep list is long because this code is genuinely subtle" | Subtle code that needs 40 explanations needs names, not paragraphs. Re-run the promotion test on every entry. |
| "This comment explains the intent" | Intent that isn't a constraint is narration. Delete. |
| "It documents why we chose this" | The decision is already made and the code embodies it. Delete. |
| "It's a docstring, so it stays" | Only if it says something the signature doesn't. Otherwise delete. |
| "It looks like a comment, so it's safe to remove" | `# type: ignore`, `//go:build`, `/* webpackChunkName */` are load-bearing. Check the reference. |
| "The code is confusing, so the comment has to stay" | Backwards. Name the value, extract the block. Comment stays only for what a name can't hold. |
| "I'll tidy this variable name too" | Only when it retires a comment. Unrelated tidying is out of scope. |
| "Promoting this needs a small refactor first" | Then don't. Keep the comment, flag it in the report. |
| "Removing it is obviously safe, skip the build" | Directive removals fail silently in review, loudly in CI. Run the check. |
| "The user said remove everything, so all of it goes" | "Everything" means the noise. Magic numbers, workarounds, and directives are the stated exceptions. |
